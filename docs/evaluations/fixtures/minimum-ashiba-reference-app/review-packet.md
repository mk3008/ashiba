# Reviewer packet

## Application semantics

This is a work-item queue. The primary review contract is explicit three-state
filtering: omitted applies no predicate, explicit null means `IS NULL`, and a
value is bound. The only sorting capability is `createdAt`, `name`, and
`priority`, with `asc`/`desc`; priority has an explicit CASE business rank and
every order ends with `id ASC`.

## Canonical SQL

Each purpose has a separate named SQL asset under `sql/`: lookup,
search, one asset per ordering capability, create, update, claim, state update,
and audit insert. The runtime selects only an existing complete list asset from
the finite application map. It never appends input to SQL.

## Transaction boundary

`app/reference-app.mjs` owns `BEGIN`, `COMMIT`, `ROLLBACK`, client release,
`FOR UPDATE SKIP LOCKED`, the claim state transition, and the JSONB audit write.
The audit table requires a `source` property. Therefore a rejected audit proves
the preceding claim rolls back rather than being silently committed.

## Machine proof summary

[`results.json`](./results.json) is generated by a runner that owns PostgreSQL
schema/data and checks lexical lowering, lookup/LEFT JOIN, BIGINT handling,
three-state behavior, hostile values/order input, CASE ordering, pagination,
RETURNING, rollback, concurrent claims, final audit state, and source marker.

## Review questions

- Is each query's purpose understandable from its asset and requirement?
- Are omitted/null/value semantics evident without reading generated glue?
- Is the finite sort capability and CASE business rule visible?
- Is it clear that runtime input does not become SQL syntax?
- Is the transaction and locking policy visible in the application facade?
- Can a schema or rule change be traced to a local query asset?

Human acceptance is still required for whether this packet is sufficient for a
real reviewer. The runner proves registered behavior, not reviewer usability or
the absence of every possible construction route.
