# Development-time lexical correctness follow-up

## Starting evidence

Merged PR #64 recorded that the development-time named-parameter compiler
incorrectly discovered a pseudo-parameter inside a nested PostgreSQL block
comment. The runtime normal precomputed-binding path does not lex canonical
SQL; it validates generated metadata and maps ordered names to values. The
correct repair point is therefore the development-time compiler.

## Ownership trace

The product path is:

1. runModelGen calls compileNamedParameters for each dialect.
2. The PostgreSQL result provides positional SQL and orderedNames.
3. analyzeQueryModel provides sourceHash and source-level optional/sort facts.
4. buildPostgresOptionalConditionCompressionBindingMetadata compiles source
   prefixes and ranges into PostgreSQL coordinates.
5. buildPostgresSafeSortBindingMetadata compiles the insertion prefix into a
   PostgreSQL coordinate.
6. compilePostgresQuery validates sourceHash, maps orderedNames to values, and
   applies only precomputed optional or sort edits when requested.

No runtime lexer was added or changed.

## Fix and permanent regression

compileNamedParameters now tracks a block-comment depth. Entering a nested
comment increments it; only the matching final close returns the scanner to
normal SQL. The permanent CLI corpus includes repeated parameters, casts,
quoted identifiers, line comments, nested block comments, untagged and tagged
dollar quotes, a function-body-shaped dollar quote, and PostgreSQL escape
strings.

The regression suite checks:

- ordered names and PostgreSQL positional lowering across the corpus;
- direct PostgreSQL execution of the artifact from runModelGen through
  pg.Client.query, without the Thin Driver;
- sourceHash equality, repeated values, and stale source rejection;
- optional compression compiled ranges after a nested comment;
- Safe Sort compiled insertion coordinate after a nested comment.

Existing adapter regressions continue to cover omitted, explicit-null,
concrete-value, multiple-omission, repeated-name, and placeholder-renumbering
execution behavior. This follow-up proves that their input metadata is
generated by the corrected product compiler for a representative nested-comment
prefix.

## Result

**ready-for-runtime-reduction.** The development-time compiler now produces a
correct registered lexical corpus artifact for direct PostgreSQL execution. It
does not itself migrate Candidate B or remove the Thin Driver. Optional
subtraction and sort insertion still need their generated coordinates and
mechanical runtime helper; named binding alone no longer requires a runtime SQL
lexer or a driver wrapper.
