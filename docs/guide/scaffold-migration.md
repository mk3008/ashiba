# Migrating from the removed feature scaffold

This breaking release preserves canonical SQL and moves the application
boundary back to ordinary TypeScript. No compatibility command or hidden
regenerator remains.

| Former surface | Golden Path replacement |
| --- | --- |
| `ashiba feature scaffold` / `feature import` | Create only the directory and application module useful to your application. Ashiba owns no feature layout. |
| generated `query.ts`, DTOs, params, result types | Existing files still compile as ordinary TypeScript. Keep or replace them with plain application-owned types. |
| generated mapper | Delete identity/simple mapping. Keep only application-specific conversion code. |
| feature query scaffold / refresh | Run `ashiba model-gen <sql> --out <bindings>` after SQL edits. |
| feature contract/check | Use `ashiba model-gen ... --check` for freshness and optional `ashiba postgres-contract` for PostgreSQL parameter/result proof. |

1. Keep the existing `.sql` file as canonical source.
2. Generate a binding artifact beside the application module:

   ```sh
   ashiba model-gen src/queries/list.sql --out src/generated/list.bindings.ts
   ashiba model-gen src/queries/list.sql --out src/generated/list.bindings.ts --check
   ```

3. Bind application-owned parameters with `bindNamedParameters`.
4. Call the native driver with its lowered SQL and separate values. The
   application owns transaction composition and rollback.
5. Use `ashiba postgres-contract` only when a PostgreSQL-derived
   parameter/result proof is useful.

## Survivability and breaking impact

- **Runtime:** already-generated modules continue to run as ordinary
  application code if their local dependencies remain installed.
- **Build:** application-owned imports/types may need local edits when they
  import a removed Ashiba DTO, mapper, or feature helper.
- **Test:** mapper-specific generated tests no longer regenerate; retain or
  replace them with application/live tests as appropriate.
- **Regeneration:** the removed feature commands cannot refresh old generated
  DTO/mapper files. Binding metadata is regenerated by `model-gen` instead.
- **Tooling/docs:** remove obsolete feature-command scripts from package.json
  and use the command catalog for current commands.

ZTD/testkit fixtures and generated logic-test assets are intentionally deferred
to Batch 3. Existing tests can stay until that separate migration is scheduled.

## Measured representative migration

The repository Support Inbox consumer was the representative Batch 2 unit. Its
canonical SQL, native `pg` execution, application-owned transactions, and
route/live tests remain. The removed regeneration boundary is the feature-query
command chain; existing generated TypeScript becomes application-owned source
pending local simplification.

| Observation | Result |
| --- | --- |
| Wall time | 18 minutes for the package-script and current-document migration unit, excluding full repository verification |
| Files changed | `package.json` and the current example README |
| Packages/config removed | no dependency or config removal; adapter/testkit migration is intentionally Batch 3 |
| Generated artifacts removed | none; existing generated TypeScript survives as application-owned source but cannot be regenerated |
| Handwritten changes | two package-script replacements and the short current-status README |
| Retries/blockers | no migration retry; no behavior blocker |
| Behavior parity | workspace typecheck and application tests pass |
| Model token usage | unavailable |
